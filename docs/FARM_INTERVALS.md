# Фарм по времени

Доработка от `main` `9d6daa5`, согласованная после исследования #50. Один новый блок
разбора показывает собственный темп фарма по пяти минутам, типы полученных добиваний
и переход к событиям выбранного отрезка на существующей шкале.

## Границы

- Самое большое наблюдаемое снижение — повод посмотреть отрезок. Это не ошибка,
  причина поражения, оценка маршрута или сравнение с нормой для героя/ранга.
- Цель и прогресс челленджа, расчёты золота/опыта, оценки и проверка роли не меняются.
- Координаты не запрашиваются новым блоком и не используются. `productReady=false`
  в координатном слое остаётся; #50 и исследовательский PR #73 не закрываются этим PR.
- Нет новых аккаунтов, хранения истории, аналитики поведения, карт или переделки CTA.

## Данные и подсчёт

1. Дополнительный alias в существующем запросе STRATZ запрашивает `numLastHits` и
   `csEvents { time isCreep isNeutral isAncient }` только для выбранного аккаунта.
   Полный состав для роли/боевых событий сохраняется. Без account ID alias выключен;
   несовпадение account/slot/hero или неоднозначный ответ не прикрепляет чужие события.
   Аргумент `players(steamAccountId: Long)` и поля проверены по сохранённой первичной
   introspection в выгрузке от 2026-11-03, не по стороннему описанию API.
2. Источник выбирается для всего нового блока. STRATZ используется для итогов и темпа,
   если каждый таймкод пригоден, число событий равно итоговому числу добиваний,
   а длительность совпадает с OpenDota. Это проверка согласованности выгрузки, не
   независимое доказательство отсутствия ошибок провайдера.
3. Иначе используются минутные накопительные счётчики OpenDota с уже нормализованным
   `times`. От начала окна идём до первого пропуска, нецелого/отрицательного значения
   или уменьшения счётчика. Показываем только покрытый префикс и его фактическую
   длительность. Пропуск не становится нулём, остаток не достраивается интерполяцией.
4. Неполные события STRATZ можно раскрыть как типы **полученной части**. Они не
   заменяют счётчик OpenDota. Категории провайдеров и минутные границы не считаются
   взаимозаменяемыми. Нулевой набор неполных событий не рисуется как нулевой фарм.
5. Тип определяется только одним явным флагом при наличии всех трёх Boolean-флагов:
   линейные, обычные нейтралы, древние. Все false, пропуски и пересечения — «тип не
   определён». NPC ID не используется для догадок. Древние не складываются повторно
   с обычными нейтралами.
6. Добивания подконтрольными существами учитываются у игрока. Одинаковые записи и
   одинаковое время не являются основанием для удаления события.
7. Окна `[начало, конец)`; событие на общей границе попадает в следующее окно.
   Последнее окно включает возможное событие в точный момент конца матча. Такие же
   границы используются при открытии событий на общей шкале. Обычный выбор одного
   события и прежние ссылки на доказательства сохраняют включённый конец.
8. Выделяется один максимальный спад между соседними полностью покрытыми окнами
   ровно по 300 секунд. Неполное покрытие и короткий финал не сравниваются. Для равных
   спадов выбирается первый; сравниваются целые количества, чтобы погрешность float
   не меняла выбор. Нет спада/сопоставимых окон — нет выделенного эпизода.

В UI остаётся один основной тренировочный CTA. Новый блок помогает выбрать эпизод
для проверки: показывает факт, ограничение интерпретации и конкретное действие
«Посмотреть события отрезка». Разбивка типов раскрывается по запросу; при полном
отсутствии данных вместо пустой карточки показана короткая строка.

Прогон использует текущий STRATZ adapter и новый анализатор, сверяет все окна,
итог, категории, пригодность времени и выбранный спад с контрольными числами.
Результат: [real-capture.json](evidence/farm-intervals/real-capture.json).
Из двух матчей на WK нельзя заключить, что все категории всех героев проверены.

```powershell
cd D:\dota-coach
node scripts/verify-farm-capture.mjs "ПУТЬ-К-СОХРАНЁННОМУ-JSON" "$env:TEMP\dota-farm-verification.json"
```

Это воспроизводимая проверка ранее полученного ответа, **не свежий запрос API**,
просмотр реплея или приёмка настоящего матча через роль-зависимый endpoint.
STRATZ-токен в окружении проверки отсутствует. Новая форма запроса, её реальная
задержка и получение alias в live API пока не проверены; проверку роли не ослабляли.
Синтетический тест проверяет привязку alias и сохранение боевых событий/позиции.

## Регрессии и UI

- Unit: границы, одновременные добивания, подконтрольные существа, неизвестные и
  пересекающиеся признаки, нулевые значения, пропуски/обрезка/регресс счётчика,
  несовпадающие длительности, отсутствие итогового счётчика, равные спады,
  сохранение тренировки/оценок/приоритетов, валидация ответа.
- Браузер: полный/частичный набор событий, отсутствие минутного ряда, пропуски и
  короткий конец; раскрытие типов с клавиатуры; переход к покупкам/смертям, включение
  нужных фильтров, фокус; ширины 320/390/768/1440. Прежний сценарий также проверяет
  челлендж 3/3 после повтора без данных, ошибки/загрузку/пустой состав и выбор игрока.
- Скриншоты текущего PR используют **синтетические данные**, что написано внутри
  изображений: [desktop](evidence/farm-intervals/farm-1440.png),
  [mobile](evidence/farm-intervals/farm-390.png); раскрытые окна и типы:
  [desktop](evidence/farm-intervals/farm-expanded-1440.png),
  [mobile](evidence/farm-intervals/farm-expanded-390.png).
- Результат локального прогона: unit **180/180**, combat **34/34**, benchmarks **8/8**,
  design **6/6**, lint, typecheck и production build — успешно. Браузерный сценарий
  прошёл полностью, без ошибок страницы: [verification.json](evidence/farm-intervals/verification.json).
  Playwright 1.62.1 / Chromium 153; API-ответы в браузерном прогоне синтетические.
- Команды: `npm run lint`, `npm run typecheck`, `npm run test:unit`,
  `npm run test:combat`, `npm run test:benchmarks`, `npm run check:design`,
  `npm run build`; `node scripts/verify-post-match-v2.mjs` с локальным Playwright и
  запущенным приложением (либо `START_SERVER=1` после build).

## Self-review полного diff

Проверены путь источники → нормализация → агрегация → контракт ответа → UI,
граничные события и переключение фильтров. Нельзя потерять данные при выборе
источника или выдать короткий/неполный интервал за спад пяти минут. Производственные
данные не подменяются фикстурами. Дополнительное поле необязательно для старого
формата ответа. Новые сырые события не отправляются в продуктовый отчёт.

нормализатор не изменены. Главный оставшийся риск — непроверенный live-запрос
