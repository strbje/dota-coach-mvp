## Что именно стало известно

| Путь | Подтверждено схемой | Ограничение для сравнения линии |
|---|---|---|
| `match(id)` / `matches(ids)` | Чтение по известному ID / списку ID | Не поиск исторической выборки по составу |
| `player(steamAccountId).matches(request)` | История указанного аккаунта; 39 полей фильтра | Зависимые наблюдения одного игрока, не общая норма для героя или ранга |
| `heroStats.stats` | `heroId/week/time/position/bracket`, `matchCount`, `remainingMatchCount`, ранние показатели | Нет аргументов обеих пар, явного патча/режима; нет исходных match IDs и полей квантилей |
| `heroStats.laneOutcome` | Попарные строки и количества исходов | Совместная группа обеих пар не установлена; прошлые несовпадения меток остаются |
| `match.laneReport` | Radiant/Dire → safe/mid/off → пять счётчиков крипов | Нет состава, роли каждого игрока, времени присутствия на линии или распределения урона |
| `heroStats.guide` → `guides` | Есть match IDs; описание указывает отбор успешных игр | Такой отбор не устанавливает обычную репрезентативную контрольную группу |

### История игрока: фильтры есть, их поведение ещё не проверено

В `PlayerMatchesRequestType` присутствуют:

- `heroIds`, `withFriendHeroIds`, `withEnemyHeroIds`;
- `positionIds`, `roleIds`, `laneIds`;
- `gameVersionIds`, `minGameVersionId`, `maxGameVersionId`;
- `rankIds`, `bracketIds`, `gameModeIds`, `lobbyTypeIds`;
- `startDateTime`, `endDateTime`, `isParsed`, `isStats`;
- `take`, `skip`, `before`, `after`, `orderBy`, `playerList`.

Описание `withEnemyHeroIds` говорит о включении **одного из** перечисленных героев,
а не обязательно всех. Аналогичное описание есть у союзного фильтра. Следовательно,
`withEnemyHeroIds: [60, 112]` **нельзя считать доказательством** состава против
Night Stalker **и** Winter Wyvern. Это вывод из контракта; фактическое OR/AND поведение
resolver ещё не проверено запросом с матчами.

Даже совпадение всех четырёх героев в матче не подтверждает 2v2: герой мог находиться
на другой линии, сменить её или прийти в ротацию. Роль/линия выбранного игрока
в фильтре не задаёт роли остальных трёх. Метка линии не измеряет проведённое там время.

Если этот путь проверять дальше, нужны:

1. Ограниченный набор **известных** матчей с положительным и отрицательным контролем
   фильтра. Для матча `9078566584` уже известны WK 42 + Oracle 111 против NS 60 + WW 112;
   несуществующее сочетание, не совпавший патч/роль и список с одним присутствующим
   и одним отсутствующим противником помогут отличить применение фильтра от совпадения.
2. Реальный ответ со всеми десятью игроками. Проверить ID, стороны, обе пары и
   подтверждённые позиции, патч/режим/ранг, период и покрытие. Не выводить позицию из героя.
3. Удалить дубликаты по match ID; считать N только после всех проверок. Пустой ответ
   не доказывает отсутствие игр, пока не проверены доступ, пагинация и фильтры.
4. Отдельно обозначать, что это история одного игрока. Даже строгая локальная
   фильтрация не превращает её в независимую выборку сопоставимых игроков.

Это план проверки, **не выполненный эксперимент**. Неизвестный максимальный `take`
не подставляется из старой REST-документации: в текущем описании после `Max :` числа нет.

### Ранние агрегаты не равны распределению

В `HeroPositionTimeDetailType` 74 поля, включая `heroDamage`, `damageReceived`,
`networth`, `xp`, `cs`, `dn`, `deaths`, `healingSelf`, `healingAllies`.
Наличие поля `Decimal` не устанавливает, среднее это, сумма или другая агрегация.
У этих полей в полученной схеме нет описаний; определения периода, индекса `time`,
знаменателя `remainingMatchCount` и пропусков также не подтверждены.

Здесь нет индивидуальных наблюдений, медианы, квартилей или дисперсии. Их нельзя
восстановить из N и одного агрегата. `heroIds` у родительского запроса не подтверждает
фильтр совместного состава: тип ответа содержит один `heroId` в строке, состав не описан.
Ранее выявленное несовпадение меток `laneOutcome` нельзя автоматически переносить
на `stats`: для него нужен собственный контроль фактического ответа.

### `laneReport` — не отчёт об агрессии

Вложенный `MatchStatsLaneReportFactionLaneObject` содержит только
`meleeCount`, `rangeCount`, `siegeCount`, `denyCount`, `neutralCount` (`Int!`).
В нём нет временных меток, участников или damage-полей. На уровне схемы не
объяснено и точное окно этих счётчиков. Поэтому этот объект не подтверждает
урон по оппонентам линии, длительность 2v2 или уход после тяжёлой линии.

## Непроверенные ветки и минимальный следующий запрос

Сбор завершился по заданному лимиту. Остались `FindMatchPlayerList`,
`FindMatchPlayerOrderBy`, `MatchPlayerType`; последнее определение уже есть
в более ранней выгрузке, но в новой повторно не запрашивалось.

Также алгоритм выбирал у корня только поля с именами match/player/heroStats/search.
Он **не заходил** в `stratz: StratzQuery`, `plus: PlusQuery`, `vendor: VendorQuery`.
Их названия или наличие не доказывают ни доступность глобального поиска, ни его отсутствие.
Другие корневые зависимости тоже не были исчерпывающе пройдены.
Общие публичные описания STRATZ и загружаемый GraphiQL не закрыли этот пробел.

Чтобы проверить эти три ветки, подготовлен **один запрос только метаданных**.
Он также получает два оставшихся enum; история аккаунтов, матчи, реплеи и
агрегаты не запрашиваются. Нужен лишь новый JSON; прошлые файлы повторять не нужно.
Токен берётся из существующего локального окружения и не записывается в файл.

  типом и защитой существующего файла. Оболочка PowerShell здесь не исполнялась.

- **Остаётся независимо от схемы:** один реальный положительный контроль устойчивого

  контрпример Anti-Mage `9079325890` его не заменяет.
